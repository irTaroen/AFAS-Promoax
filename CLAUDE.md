# Promax — AFAS ↔ Salesbuildr Integration

PowerShell scripts that synchronise data between **AFAS Profit** (ERP) and **Salesbuildr** (CPQ/sales platform) for the customer Promax.

## Project layout

| Path | Purpose |
|---|---|
| `Sync-Forecasts.ps1` | Four independent flows, each with its own watermark: **Flow 1** AFAS Forecasts → Salesbuildr Opportunities; **Flow 2 (Items)** creates missing articles (`FbItemArticle`) for won closed Opportunities; **Flow 3 (Quotations)** creates the AFAS quotation (`KnQuotation`, voorcalculatie) and closes the originating AFAS Forecast; **Flow 4 (PDF)** attaches the SB quote PDF to the AFAS quotation as a dossieritem (`KnSubject`) |
| `configs/mapping-artikelgroepen.xml` | Maps a Salesbuildr **main (root) category** id (`SB-maincat-id`) to the AFAS artikelgroep (`Grp`) used when creating articles (Flow 2) — a quote line's leaf `category.id` is walked up to its main category before this lookup |
| `configs/config.xml` | Runtime config, **plaintext, gitignored**: mode (TEST/PROD), `<flows><flow1>/<flow2>/<flow3>/<flow4>>` on/off toggles, AFAS environment number + token, connector names (incl. `<afas><connectors><dossieritems_get>` = `Salesbuildr_Dossieritems`, `<subject_update>` = `KnSubject`), Salesbuildr URL/API key, country mapping, `<salesbuildr><diensten_maincategory_id>` (SB "Diensten" main-category id, defaults to `UyOpp42UPGy3LKgSOQGX` when absent), `<afas><kn_subject_stid>` (dossieritemtype, default `46`) and `<kn_subject_usid>` (AFAS user for the dossieritem, default `53307._sa_salesbldr`) — both used only by Flow 4 |
| `configs/config.example.xml` | Committable config template with `{afas_token_data}` / `{salesbuildr_api_key}` placeholders |
| `configs/LastSyncDates.xml` | Single sync watermark state file, plain XML (`<SyncDates><OverrideDays>/<Flow1>/<Flow2>/<Flow3>/<Flow4></SyncDates>`), one node per flow plus an optional `<OverrideDays>` test override; gitignored via `configs/Last*.xml` |
| `logs/log.txt` | Summary run-log, newest run first (see "Summary run-log" below); `logs/` is gitignored |
| `Modules/Logging.psm1` | Structured logging helper |

`configs/` is created automatically by the script if missing.

## Business flows

Organisations & contacts have no dedicated sync script at the moment.

**Credential pre-check**: right after `Connect-Afas`/`Connect-Salesbuildr`, before any flow runs, `Test-AfasConnection` (light `GET {AfasRestUrl}/metainfo`) and `Test-SalesbuildrConnection` (light `GET {SalesbuildrUri}/public-api/opportunity?size=1`) each return `$false` on HTTP 401 (other errors bubble up); both are checked (not short-circuited) so one run surfaces both an invalid AFAS token and an invalid Salesbuildr key, each logged as its own WARNING — if either fails the script `return`s immediately, no flows run, watermarks untouched.

1. **Forecasts ↔ Opportunities ↔ AFAS voorcalculatie/dossier** (`Sync-Forecasts.ps1`, self-contained, no `Modules/` dependency yet) — four independent flows, each with its own config toggle and watermark node, run in sequence within one script invocation:
   - **Flow 1 — AFAS Forecasts → Salesbuildr Opportunities**: delta sync via the `Flow1` node in `configs/LastSyncDates.xml`; fetches changed forecasts (`gewijzigd` filter, operator 4 = greater than — note `5` is *less than*; the datetime value must be local time `yyyy-MM-ddTHH:mm:ss`, a trailing `Z` triggers a server error); links each Opportunity to its Company via `companyExtId = "afas-Organisatie-{organisatie}"` (the same key the org-sync writes — **not** `verkooprelatie`); if that Company does not exist in Salesbuildr the forecast is logged (WARNING) and skipped; sets the **owner** (required by the API) via `ownerId = verantwoordelijkeOwnerID` (the GetConnector resolves the responsible AFAS employee to their SB user id — the owner is a SB *user*, not a Contact, so it cannot be looked up by e-mail); resolves the **client contact** from `contactpersoonMail` via `Get-SalesbuildrContactByEmail` (`GET /public-api/contact?query={email}`, exact `email` match) and sets `contactId` — **required**, same as the Company check: no e-mail or no matching contact logs a WARNING and skips the forecast entirely (watermark held for retry, `$Flow1Complete = $false`), the Opportunity is not upserted; sets `externalIdentifier = "afas-Forecast-{forecast}-{volgnummer}-{verkooprelatie}"` (e.g. `afas-Forecast-11310-42-10654`) — encodes three distinct `Salesbuildr_Forecasts` fields (`forecast` = globally-unique AFAS forecast id, used as the AFAS quotation's `QuId`; `volgnummer` = CmForecast `SqNo`; `verkooprelatie` = CmForecast `PrId`, the debtor code) so Flows 3 and 4 can parse the CmForecast key straight from the identifier with **no re-fetch**; upserts via `PUT /public-api/opportunity/ext/{externalIdentifier}`; skips if the Opportunity is already `statusId: "closed"` in Salesbuildr.
   - **Flow 2 — Items: create missing AFAS articles for won closed Opportunities**: delta sync via the `Flow2` node; fetches closed Opportunities (`statusId: "closed"`, `size`/`from` pagination) independently of Flows 3/4 (own watermark, own call to `Get-SalesbuildrClosedOpportunities`); categorizes Won/Lost via the shared `Split-ClosedOpportunities` helper (identical logic used by Flows 2/3/4: primary quote `primary: true`, **no fallback** to any other approved quote; missing/unapproved primary quote = Lost, not an error). Only Won lines matter here — Lost is a no-op for Flow 2. Flattens all Won quote lines, resolves each via `Resolve-AfasLineItem` (see below), and collects unique item codes for lines with `Kind = 'artikel'` (i.e. an `mpn`). Per unique `mpn`: checks existence via `Get-AfasArtikelByItemCode` (targeted `Salesbuildr_Artikelen.itemCode` lookup — not a bulk catalog fetch, AFAS holds 30,000+ articles); if missing, resolves the artikelgroep (`Grp`, see below) and creates it via `New-AfasArtikel` (`FbItemArticle`). An unmapped category logs a WARNING and clears `$Flow2Complete` (watermark held) but does **not** skip anything else — Flow 2 has no opportunity-level skip concept, it just fails to create that one article; Flow 3 will independently detect the still-missing article next run and skip the opportunities that reference it. **Flow 2 never creates Diensten items** (`Kind = 'diensten'`) — those are resolved to werksoort/TXT lines entirely inside Flow 3 — and it never creates the AFAS quotation or closes the Forecast.
   - **Flow 3 — Quotations: create the AFAS quotation and close the Forecast**: delta sync via the `Flow3` node; fetches closed Opportunities independently (own watermark) and categorizes Won/Lost via the same shared `Split-ClosedOpportunities` helper. Stap 3a: categorize. Stap 3b: resolve every Won line via `Resolve-AfasLineItem`; for each unique non-blank Diensten `internalProductId`, check existence in AFAS (`$DienstenExists` — never added to `$FailedItemCodes`, never created here); for each unique artikel `mpn`, check it **already exists** in AFAS (`$FailedItemCodes` if missing — this is the article-availability check, not creation; creation is Flow 2's job, so a disabled/failed/not-yet-run Flow 2 surfaces here as a missing article). Stap 3c (Won, per opportunity): parses `ForecastId`/`SqNo`/`PrId` from the Opportunity's `externalIdentifier` via `ConvertFrom-ForecastExternalId` — no re-fetch of the Forecast; idempotency check via `Get-AfasQuotation` filtering `Salesbuildr_Voorcalculatie` on `offerte = {ForecastId}` (`$QuotationExists`) — **if it already exists, only creation is skipped** (logged), execution still falls through to closing the Forecast (idempotent `PUT`), so a prior run that created the quotation but crashed before closing the Forecast completes on the next run instead of retrying the creation forever; **else** (creation branch) any Won line that's unmappable (no `mpn`, not Diensten) or an artikel line whose `mpn` is in `$FailedItemCodes` causes the **whole opportunity** to be skipped (WARNING, `$Flow3Complete = $false`, no quotation, Forecast stays open) — Diensten lines are **exempt**, they always resolve to a werksoort or TXT line and can never trigger this skip; otherwise builds the line array and creates the **AFAS quotation** (`KnQuotation`, voorcalculatie, `Ds` = the SB quote's `title` capped at 100 chars) via `New-AfasQuotation`; then **unconditionally** closes the originating AFAS Forecast (`PUT CmForecast`, `ViOp = "G"`, `OrAF` = total quote amount = Σ `price × quantity × (1 - discount)` over quote items), for both the just-created and the pre-existing-quotation case. Stap 3d (Lost, per opportunity): parses the same key and closes the Forecast (`ViOp = "N"`, no `OrAF`, no articles/AFAS quotation) — a missing/unapproved primary quote is **not** an error, it's a legitimate Lost outcome that still advances the watermark. See `Get-AfasQuotation` / `New-AfasQuotation`.
   - **Flow 4 — PDF: attach the SB quote PDF to the AFAS quotation**: delta sync via the `Flow4` node; fetches closed Opportunities independently (own watermark) and categorizes via the same shared helper — Lost opportunities are a legitimate no-op (no PDF, not a skip, watermark still advances). For each Won opportunity: parses `ForecastId`/`PrId` from `externalIdentifier` via `ConvertFrom-ForecastExternalId` — no re-fetch. **Precondition**: the AFAS quotation must already exist in `Salesbuildr_Voorcalculatie` (`Get-AfasQuotation` filtering `offerte = {ForecastId}`, same check Flow 3 uses) — if Flow 3 hasn't created it yet (this run or a prior one), Flow 4 holds the watermark and retries next run rather than attaching a PDF to a non-existent quotation. **Idempotency**: `Get-AfasQuotationAttachment` queries the `Salesbuildr_Dossieritems` GetConnector server-side filtered on `Offerte = {ForecastId}` (operatortypes=1); a row with `Type == StId` (the configured dossieritemtype) and `Ja_Nee == true` means the PDF is already attached → skip — this matters because the `KnSubject` POST is **not** idempotent (unlike Flows 1/3's `PUT`s), so without this check a re-run would create duplicate attachments. **PDF fetch**: `Get-SalesbuildrQuotePdf -QuoteId` does `GET /public-api/quote/{id}/pdf` via `Invoke-WebRequest` directly (**not** the JSON wrapper `Invoke-SalesbuildrRequest`, which would corrupt binary), reading `RawContentStream.ToArray()`; HTTP 404 or an empty response → `$null` (logged, watermark held). **AFAS upload**: `New-AfasSubjectAttachment` POSTs `KnSubject` with `StId` (config `<afas><kn_subject_stid>`, default `46`), `Ds = "SB Offerte - {ForecastId}"`, `Da` (current datetime), `UsId` (config `<afas><kn_subject_usid>`, default `53307._sa_salesbldr`); a `KnSubjectLink` sub-object (`ToSR=true`, `SfTp=4` always, `SfId = {verkooprelatie/PrId}`, `QuId = {ForecastId}`) links it to the relation + offerte; a `KnSubjectAttachment` sub-object carries `FileName = "SB-Offerte-{ForecastId}.pdf"` and `FileStream` = the Base64 PDF. Any error (fetching the primary quote, parsing the external id, fetching the PDF, or the `KnSubject` POST) clears `$Flow4Complete` and holds the watermark for retry.
   - **Ordering dependency, run independently**: Flow 2 (Items) prepares the articles that Flow 3 (Quotations) references, and Flow 3 creates the quotation that Flow 4 (PDF) attaches to — but each flow still fetches its own closed-Opportunities batch and advances its own watermark; none of them block on another flow being enabled in the *same* run. Flow 3 tolerates Flow 2 being disabled/failed/behind by re-checking article existence itself (and skipping just the affected opportunities); Flow 4 tolerates Flow 3 being disabled/failed/behind by holding its own watermark until the quotation shows up.
   - **Flow toggles**: each flow can be switched on/off independently via `configs/config.xml`'s `<flows><flow1>/<flow2>/<flow3>/<flow4>>` (`ConvertTo-ConfigBool`: accepts `true/1/yes/ja/on` and `false/0/no/nee/off`, case-insensitive; empty/missing/unrecognized → default **true**, so a config without `<flows>` still runs all four flows). A disabled flow is skipped entirely (logs `"=== Flow N is uitgeschakeld in config.xml ... ==="`) and its watermark node is left untouched (logs `"Flow N uitgeschakeld — state ongewijzigd"`) — no warning, since nothing was attempted. Each flow also has an internal `$AfasWritesOnHoldN` dry-run switch (hardcoded `$false` in the script, not config-driven) that, if flipped to `$true`, fetches/categorizes/logs as normal but skips every AFAS write and holds that flow's watermark — a way to inspect a flow without mutating AFAS.
   - **Watermark**: all four flows' watermarks live as sibling nodes (`<Flow1>`/`<Flow2>`/`<Flow3>`/`<Flow4>`) in the single plain-XML state file `configs/LastSyncDates.xml` (no more `Export-Clixml`/`Import-Clixml`), read via `Get-SyncWatermark -Path -Name` (missing file/node → `2026-01-01`) and written via `Set-SyncWatermark -Path -Name -Date` (round-trip `'o'` format; touches only its own node, so all four flows stay independent). Each flow advances its node **only if every record in the batch was processed successfully** (`$Flow1Complete` / `$Flow2Complete` / `$Flow3Complete` / `$Flow4Complete`). Any skip (missing org, unmapped category, unavailable article, quotation not yet created) or error holds the date so the next run retries those records; a Lost categorization is **not** a skip and still advances the watermark once its Forecast is closed successfully (Flow 3) or once Flow 4 has confirmed no PDF is needed; all four flows advance independently. An optional `<OverrideDays>N</OverrideDays>` sibling node is a **test override**: an integer N makes all four flows sync from N days ago at local midnight for that run instead of their own watermarks (`Get-SyncOverrideDays`, logs a WARNING when active); empty/missing is ignored, non-numeric is ignored with a WARNING. `Set-SyncWatermark` never touches `OverrideDays`, so once set it stays active on every run until manually cleared.
   - **Summary run-log**: alongside the existing console `Write-Log`, each run also prepends one block to `logs/log.txt` (relative to the script root, gitignored, NEWEST-FIRST — older runs get pushed down). A block starts with a `RUN <timestamp>` header, then one section per flow in fixed order — an optional `Algemeen (setup & credentials)` bucket (only present if there were setup/credential WARNING/ERRORs) followed by Flow 1–4. Each section has a `Status :` line (`SUCCES — state bijgewerkt` / `ONVOLLEDIG — state NIET bijgewerkt, herkansing volgende run` / `UITGESCHAKELD — state ongewijzigd`, derived from that flow's Enabled + Complete flags), a timestamped `Aangemaakt/verwerkt (N):` list (Flow 1 opportunity upserts, Flow 2 created articles, Flow 3 created quotations + closed Forecasts, Flow 4 attached PDFs), and a timestamped `Waarschuwingen/fouten (N):` list of every WARNING/ERROR from that flow (INFO stays console-only). Implemented via globals `$Global:FlowLabel`/`$Global:CurrentFlow`/`$Global:RunLog`/`$Global:FlowStatus` and helpers `Get-FlowLogBucket`, `Add-CreatedObject`, `Set-FlowStatus`, `Write-RunLogFile` (called in a `finally`, so a fatal error or an aborted credential pre-check still writes a block). Independent of, and in addition to, `Modules/Logging.psm1` (still unused by this script).
   - Field mappings and exact JSON payloads: see the "Promax Implementation Notes" sections in [AFAS_API_Guide.md](docs/api/AFAS_API_Guide.md) and [Salesbuildr_API_Guide.md](docs/api/Salesbuildr_API_Guide.md).
   - **Item code (`ItCd`) & line type (`VaIt`)**: each quote line is resolved to an AFAS item code and line type by `Resolve-AfasLineItem -Line -CategoryParentMap -DienstenMainCategoryId` — called independently by Flows 2 and 3, each on their own fetched batch of Won lines. **mpn present** → `ItemCode = mpn`, `VaIt = "2"` (artikel) — unchanged: used for both the "does the article exist?" lookup (`Salesbuildr_Artikelen.itemCode`, a targeted per-`mpn` filtered GetConnector call, not a bulk catalog fetch — AFAS holds 30,000+ articles) and creation (`FbItemArticle.ItCd`, Flow 2 only). **No mpn, but the line's main category (resolved via `Get-SalesbuildrMainCategoryId`, same walk-up-to-root as the `Grp` lookup below) is "Diensten"** (`configs/config.xml`'s `<salesbuildr><diensten_maincategory_id>`, SB main-category id `UyOpp42UPGy3LKgSOQGX` by default) → `ItemCode` = the line's **`internalProductId`** (or `''` if the product has none), `Kind = 'diensten'`. The **old `"AFAS werksoort"` custom-field branch is removed entirely** — a consequence is that any werksoort must now sit under the Diensten main category. `internalProductId` is read by the new `Get-SalesbuildrProductInternalId` helper, which **always** does a full `GET /public-api/product/{id}` fetch (`Get-SalesbuildrProductById`, cached in `$Global:SbProductCache`) — the inline quote-line `product` reference (`IdentifiedEntityResponseDto`) never carries `internalProductId` (only id/name/externalIdentifier/labels/customFields). **Neither mpn nor Diensten** → the line is unmappable. **Diensten existence check** (Flow 3, Stap 3b): for each unique non-blank Diensten `internalProductId`, `Get-AfasArtikelByItemCode` checks `Salesbuildr_Artikelen.itemCode` (same lookup as for articles), stored in `$DienstenExists` — Diensten codes are **never** added to `$FailedItemCodes` and **never created** via `FbItemArticle` (not by Flow 2, not by Flow 3). `New-AfasQuotation` (Flow 3) turns a Diensten line into one of two shapes: **exists in AFAS** → werksoort line (`VaIt="1"`, `ItCd = internalProductId`, `UnId=""`, `AmCo="0"` **always**); **not found (or blank `internalProductId`)** → TXT line (`VaIt="3"`, `ItCd="SBO"`, `Ds` = `"{name} - aantal {qty}, prijs {price}, kostprijs {cost}"` capped at 255 chars, `UnId`/`QuUn`/`Qu`/`QuSa`/`Upri`/`AmCo` all empty strings) — so a Diensten line can **never** cause a whole-opportunity skip. **Enforcement** (Flow 3, Stap 3c) applies only to article lines and non-Diensten no-mpn lines: if any such line of a Won opportunity is unmappable, or references an artikel that isn't (yet) in AFAS, the **whole opportunity** is skipped — no AFAS quotation is created and the Forecast stays open (watermark held for retry). `New-AfasQuotation` sets `VaIt` per line from each Regel's `Soort` field (falls back to `"2"` if absent).
   - **Article group (`Grp`)**: a new AFAS article's artikelgroep (required, Flow 2 only — Flow 3 never creates articles) is resolved in a **two-hop main-category lookup**. At the **start of the run**, `Get-SalesbuildrCategoryParentMap` fetches all SB categories via `GET /public-api/category` (flat list; each `CategoryResponseDto` carries `parentCategoryId`) and builds an in-memory `category.id -> parentCategoryId` map (`$CategoryParentMap`; empty string = root). When a quote line is processed, `Get-SalesbuildrMainCategoryId -CategoryId -ParentMap` walks the line's leaf `category.id` up the parent chain to its topmost/root **main category** (has cycle protection; returns `$null` if the category id is unknown to the map). That main-category id is then looked up in `configs/mapping-artikelgroepen.xml` (`<categorie SB-maincat-id="..." AFAS-id="..." AFAS-naam="..."/>`) to get `Grp`. Only categories with a non-empty `AFAS-id` are loaded; a main category missing from the file (or with an empty `AFAS-id`), or a leaf category that cannot be resolved to a main category, is "not mapped" and Flow 2 skips creating that article (WARNING, `$Flow2Complete = $false`, watermark held for retry) — the article stays missing in AFAS, so Flow 3 will subsequently detect it via its own existence check and skip the opportunities that reference it (a partial AFAS quotation must not reference a non-existent article); `AFAS-naam` is logging-only. `configs/config.xml`'s old `<afas><artikelgroepmapping><costcenter>` block has been removed entirely (superseded by `configs/mapping-artikelgroepen.xml`). See `Get-SalesbuildrCategoryParentMap`, `Get-SalesbuildrMainCategoryId`, `Get-AfasArtikelgroep` (now takes `-CategoryParentMap`), `New-AfasArtikel`.

## AFAS connector mapping (from configs/config.xml)

| Purpose | Flow | GetConnector | UpdateConnector |
|---|---|---|---|
| Forecasts / Opportunities | Flow 1 | `Salesbuildr_Forecasts` | `CmForecast` |
| Articles / Products | Flow 2 (Items) | `Salesbuildr_Artikelen` | `FbItemArticle` |
| Voorcalculatie / Quotes | Flow 3 (Quotations) | `Salesbuildr_Voorcalculatie` | `KnQuotation` |
| Attachments / Dossieritems | Flow 4 (PDF) | `Salesbuildr_Dossieritems` | `KnSubject` |

Note: Flows 1 and 3 also write to `CmForecast` (`PUT`, closing the Forecast `G`/`N`); `Salesbuildr_Forecasts`/`CmForecast` above reflects Flow 1's read/write, while Flow 3 reads `Salesbuildr_Voorcalculatie`/writes `KnQuotation` and `CmForecast`.

AFAS environment number: **53307** (`https://53307.rest.afas.online/profitrestservices`).  
Salesbuildr base URL: **`https://verkoop.promax.nl/public-api`** (tenant `promax`).

## Credentials

Credentials are stored **plaintext** in `configs/config.xml` (no DPAPI, no encryption) — the file is gitignored; `configs/config.example.xml` is the committable template with `{afas_token_data}` / `{salesbuildr_api_key}` placeholders.  
**Never write actual tokens or keys into code, docs, or commit messages.** Use placeholders like `{afas_token_data}` / `{salesbuildr_api_key}` in examples.

- AFAS auth: `Authorization: AfasToken {base64(xml_token)}` — the full `<token>…</token>` XML (stored in a CDATA block, read via `$config.SelectSingleNode('afas/token').InnerText`) is Base64-encoded at runtime.
- Salesbuildr auth: `api-key: {api_key}` request header.
- Both credentials are validated at startup (see "Credential pre-check" above) before any flow runs.

## PowerShell conventions

- `$ErrorActionPreference = 'Stop'` everywhere — let exceptions bubble.
- AFAS token encoding: `[System.Convert]::ToBase64String([System.Text.Encoding]::ASCII.GetBytes($token))`.
- Config is read from `configs/config.xml` (plaintext, gitignored) via each script's local `Read-XMLConfig` helper — no encryption, no `Configuration` module; the AFAS token is read via `$config.SelectSingleNode('afas/token').InnerText` (works with the CDATA block).
- Log via `Write-Log -Level INFO|WARNING|ERROR -Message '...'`.
